# Standalone profile unlock, 20 September 2026

Scope: ID-02-LOCAL, AUTH-002 and the local-profile portion of SEC-002. Browser product acceptance is verified. Native protection and biometric integration are implemented; actual OS-protected PIN/restart and physical Touch ID acceptance remain required. No complete original requirement or platform release gate is closed.

## Implemented behavior

- Existing profiles retain their passphrase, ciphertext format and IndexedDB version. Optional quick-unlock metadata is part of the existing vault row. Enrollment, replacement and removal require the original passphrase and increment the profile revision in one transaction. Other open sessions lock; stale writers cannot restore an older credential.
- Browser PINs contain 8–12 digits. PBKDF2-SHA-256 at 600,000 iterations derives an AES-GCM wrapping key. Authenticated data binds the wrapper to the profile and a new credential epoch. Only the temporary passphrase-verified enrollment key is extractable; ordinary passphrase and PIN sessions use nonextractable keys. The UI explains the weaker guessing resistance of a PIN if browser data is copied.
- Five failed attempts introduce a 30-second delay, doubling up to 15 minutes. Web Locks serialize attempts for each profile. Counters persist through reloads and ordinary encrypted record saves. Passphrase-authorized replacement remains available for recovery.
- Profile removal and restoration clear quick-unlock credentials while preserving encrypted business data. Cancelled enrollment, competing writes, corrupt settings, transplanted wrappers and delayed native results cannot grant a stale session. A rejected PIN never appears as an unlocked profile.
- Desktop PIN wrappers receive additional OS protection through a bounded, typed preload capability. The main-process envelope binds profile, epoch and method. A biometric envelope cannot be opened through the PIN method. Supported Touch ID enrollment and unlock require a prompt; unavailable protection has no plaintext/session-only fallback. Actual encryption/decryption also checks asynchronous provider readiness.
- The existing standalone renderer vault still performs WebCrypto and owns decrypted session data. Native key unwrapping is a narrow capability, not completion of utility-process key custody or full-file desktop encryption. Those implementation requirements remain ID-03.

The wrapping mechanism follows the [Web Cryptography API](https://www.w3.org/TR/webcrypto/). Native protection uses [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage); its guarantees and availability depend on the OS provider. Real Keychain access can require interaction, so unsigned unattended tests do not establish signed desktop provider acceptance.

## Recovery-clock correction

The corporate regression initially rejected a genuinely new session: its database timestamp was milliseconds behind the browser's recovery-start timestamp. The trace showed the new session at `23:06:04.825Z` while the recovery request was already underway. Comparing independent wall clocks was incorrect.

A public, uncached, typed `/api/v1/identity/recovery-clock` endpoint returns only database time. Recovery intent and session issuance are ordered on that clock; the recent-authentication check uses the database observation captured with the session. The existing recovery response shape is unchanged. The client maps remaining reset authority onto its local clock conservatively, accounting for request time. Tests cover browser clocks one hour ahead and behind, same-session rejection, proof older than the server-clock intent, expired proof and policy changes. This preserves the fresh-session requirement rather than adding an arbitrary clock-skew grace period. Real-provider acceptance remains open.
