# SDK-01: scoped business releases by default

16 September 2026. New personal and company workspaces initialize Orders and Inventory 2.0 directly on their scoped public SDK backends. Existing schema-1 workspaces retain their historical contracts until an administrator performs the reviewed coordinated upgrade. This is local functional acceptance, not full platform parity or production release acceptance.

## Behavior

- Current authoring entry points export the reviewed 2.0 definitions and scoped handlers. Immutable Orders 1.1 and Inventory 1.2 definitions/backends remain available for historical workspaces, version-bound pending work and receipt recovery. Catalog discovery deduplicates identical reexported backends while rejecting distinct backends with the same identity.
- Trusted onboarding initializes empty module namespaces at their declared schema versions and records one initialization audit per module. It does not invent migration history. The reviewed product template explicitly grants Orders its four declared Inventory services and gives Sales/Warehouse the reservation permission needed for their existing business actions. API callers cannot supply this template or grant themselves permissions. Production entitlements remain inactive and activations remain drafts pending the existing commerce/publication controls.
- New stock, orders, reservations and fulfillment use module-owned private records, scoped locks, declared public services and atomic audit/outbox/receipt behavior. Historical unversioned write routes return an actionable schema incompatibility response before touching retired SQL storage. An already accepted historical receipt remains recoverable.
- Development seed and load fixtures now use the public SDK operations. Historical integration and conversion tests explicitly select their archived templates, so changing the default cannot silently reinterpret their inputs.

## Performance and restore

The first local scoped workload failed confirmation at **1,067 ms**, with reads at **494 ms**. Its [original report](load-before-optimization.json) is retained; its fixture already used scoped SDK operations, before the report gained explicit backend/version fields. Confirmation profiling found 300 full-registry metadata reads across 50 requests. Resolution now loads all candidate versions in the transitive dependency closure rather than unrelated registry manifests. Cycles terminate; dependency backtracking, pins, signature checks, current policy and authorization remain enforced. No permission or entitlement cache was introduced.

The uninstrumented repeat passed at 390/848 ms; the final audited-fixture [run](load.json) passed at **394/863 ms** for reads/confirmation, against unchanged **500/1,000 ms** limits. The dataset remains 1,000 orders, one product, 50 concurrent HTTP clients sharing one actor and stock record. These local timings do not establish remote CI acceptance or production capacity.

The [restore drill](restore.json) now reconciles both migrated business workspaces and namespaces initialized by the trusted host. It verifies balances, movements, reservations, orders and numbering, along with schema history, RLS and the retired-storage write fence. An empty newly initialized workspace may lack its lazy order counter; a migrated workspace or a workspace containing orders may not. Initialization and migration counts can overlap. Managed recovery and full service restoration remain OPS-03.

Its two-core runner reported Intel Xeon Platinum 8370C. It predates the current scoped defaults and dependency-closure optimization. OPS-07 remains open until the current candidate has remote acceptance.
