# SDK-02: retained local versions and lifecycle history

16 September 2026. Retained releases can now be selected through the local module interface, with compatibility explanations before review. Successful installations and removals have persistent, profile-local history. This closes the local acceptance work tracked by SDK-02; broader SDK, identity, synchronization, application and release gates remain open.

## Implementation

- The planner and installer share the same starting local schema calculation. Planning excludes releases that cannot use the saved schema or lack a complete declared forward migration path. Dependency resolution can select a compatible retained provider instead of choosing a release that will inevitably fail on the stored data.
- The retained-version view evaluates the whole active consumer set. Compatible releases open the existing configuration/dependency review. Incompatible choices are disabled with a reason; selecting older code never reverses saved data migrations. The signed worker still validates actual records and migration execution before any installation becomes active.
- Installation events commit atomically with the accepted release/data set. Removal events commit with local deactivation. Retries of accepted installation receipts add no duplicate events. Failed or interrupted migrations do not enter successful history.
- History stores module names/versions and timestamps inside the same encrypted profile. It has a paged local view and remains available after uninstall, restore and unlock. Historical accepted attempts without completion timestamps show their known request time explicitly. No corporate telemetry or corporate audit authority is inferred from personal history.
- Version and history views use the existing semantic stacked-list layout. A first table implementation was replaced after narrow-screen inspection exposed cramped explanations. Navigation clears obsolete success notices and starts at the panel heading. No global styling changed.

## This checkpoint's verification

- **155 unit/PostgreSQL tests in 30 files**, strict type/boundary/copy checks and all four builds passed. A final build passed after the list refinement.
- New planner tests cover incompatible rollback, missing migration paths and selection of an older compatible dependency. History tests cover legacy request timestamps, duplicate suppression and commit ordering for equal timestamps.
- **Nine distinct headless browser cases** passed across local workers, controls, dependency coordination, downloads and version history. The new journey installs 1.0, migrates actual records to schema 2, retains compatible 1.1 code, returns to 2.0, then selects 1.1 offline using keyboard activation. Incompatible 1.0 is disabled. Records keep schema 2 and their original data; the selected release retains its configuration. Removal/restoration and profile unlock preserve all seven successful history entries. Scoped Axe checks pass; this is not whole-product accessibility certification.
- **Three minimized/unfocused native cases** passed. The packaged-module case recovers across process restarts, verifies two successful coordinated installation events and no duplicates after repeated receipt recovery, exposes both modules in history, and disables the incompatible retained release. Native controls and encrypted worker restart regressions also pass. Actual compatible version switching is exercised by the browser journey; native evidence covers retained availability/history and the existing worker migration/recovery path.
