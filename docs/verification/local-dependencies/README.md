# SDK-02: coordinated local module dependencies

16 September 2026. Local installation now resolves the complete active module set, reviews all changed releases and configurations, and commits their migrations together. Restoring a retained module can also restore its retained dependencies while offline. SDK-02 and overall parity remain active.

## Behavior and boundaries

- `resolveReleaseSet` resolves multiple roots together with backtracking. Explicit pins remain fixed; preferred versions keep compatible existing modules unchanged. Dependencies are returned before their consumers. Cycles, incompatible hosts and unsatisfiable consumer ranges fail closed. The existing single-root `resolveReleases` delegates to the same resolver.
- `planLocalInstallation` includes every active consumer, so selecting a new provider can require a reviewed compatible consumer update. Unrelated compatible releases retain their existing versions. The personal registry supplies only enabled, assigned and entitled candidates. Each selected download rechecks server access and its signature; a release version changing during download requires another review.
- `LocalSession.installSet(rootModuleId, releases, options)` verifies every signed package and configuration before staging. It validates the complete resulting active set, outstanding operation requests and immutable installed bytes. Duplicate modules or an absent root are rejected.
- The encrypted installation attempt retains the exact root and related packages/configurations. Each migration executes against its own private namespace. No executable or migrated record becomes active until every selected worker succeeds and one compare-and-swap commit records the complete set and acceptance marker.
- A later migration failure discards earlier workers' provisional results. Cancellation, profile lock and restart preserve the previous active set. Recovery rechecks current constraints and resumes the entire selection. Overlapping unfinished attempts and removal of an affected module require explicit resolution or discard. Completed attempts retain compact version metadata; replay cannot reinstall an older set.
- The existing local module dialog displays related release versions and separate schema-derived configuration forms. The review starts at its heading when the selected release changes. Offline restoration plans against retained signed packages and retains each module's configuration and data.

## Verification

New resolver cases cover cross-root backtracking, consumer upgrades, unchanged unrelated preferences, explicit pins, cycles, incompatible hosts and offline retained-set planning. All four production builds passed.
- **Six distinct focused headless Chromium cases** passed. The new runtime journey builds/publishes independent provider and consumer packages using the CLI's existing `--dependency` input. It rejects a provider-only incompatible update and a corrupt dependency, verifies that a later consumer migration failure preserves both installed modules and all records, blocks overlapping removal, then cancels, unlocks and resumes the entire staged set offline. Both schemas advance once; acceptance replay preserves the result and each saved configuration.
- The interface journey installs a new dependency automatically, reviews configuration separately, proposes a compatible consumer update when upgrading its provider, migrates both saved records, removes both modules in dependency order and restores the retained set offline. A new operation after restoration uses the retained configuration. Revoking a dependency entitlement after discovery denies the subsequent download and installs neither module.

The expanded package journey terminates the native application during a two-module update, restarts, unlocks and resumes the entire selection through the real UI. Both stored schemas/history entries are checked, together with historical operation receipts and the actual packaged worker URL under native CSP. Native windows remain minimized and unfocused.

## Remaining work

Verified downloads are staged after the complete review is prepared; interruption before profile staging can still require redownloading packages. Durable partial-download recovery, local-profile fleet reporting, a general retained-release rollback selector and broader schema/custom-view coverage remain open. Local migrations and worker capabilities do not grant corporate service access. Personal-to-company import, full-file native SQLite encryption, hosted trust rotation and full release acceptance remain separate requirements.
