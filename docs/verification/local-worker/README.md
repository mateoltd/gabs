# SDK-02: local worker and encrypted transaction foundation

16 September 2026. Standalone resource saves now run in a dedicated worker on web and desktop, then commit records and retry receipts together to the encrypted profile. The local-profile interface retains its existing layout. SDK-02 remains active: independently distributed local-handler bundles, installed custom operation flows and compatible local-handler upgrades still need implementation and acceptance.

## Contracts and execution

- `@suite/module-sdk/local` provides `defineLocalModule` and `createLocalModuleClient`. Inputs, outputs, business errors, configuration and resource data come from the existing module definition. The local API only admits `local` operations and explicitly standalone resources; corporate handlers stay in `defineModuleServer`. Invalid resource names, missing handlers, corporate operations and malformed typed inputs fail compilation. Runtime checks remain authoritative within the local host.
- Reviewed `module-local.ts` files are discovered into a worker-only catalog without editing host registries. Current production modules have no custom local operation handlers yet. This bundled discovery is not independently installable executable distribution; that work remains open.
- Local handlers receive a profile ID, request ID, configuration, typed standalone resources and typed rejection. They receive no corporate transaction, cross-module service, credentials or desktop bridge. Workers isolate computation and can be terminated; reviewed application code is not a sandbox for hostile publishers.
- Each call computes against a private snapshot. Declared resource capabilities enforce module/version scope, standalone support, append-only behavior and optimistic versions. Caught capability failures abort the transaction. Reusing a request key returns its original result; changing its input or configuration is rejected. Local receipts never authorize corporate effects.
- The host serializes each profile's transactions and saves their records and receipts in one AES-GCM encrypted IndexedDB value. A transactional revision check rejects a stale session or a removed profile. Existing vaults without a revision remain readable. Returned profile data is a detached snapshot; mutating it cannot bypass worker execution.
- Cancellation, a time limit, worker failure or profile lock before commit prevents a save. A save whose durable commit has started can complete; callers must reuse its request key after unlock to recover an uncertain outcome. Locking also terminates active workers. Automatic pending-operation recovery across profile removal/sign-out remains OFF-03; the UI does not yet offer a custom operation queue/cancel flow.

## Verification scope

- Strict TypeScript, dependency boundaries, UI-copy checks and **138 unit/PostgreSQL tests across 26 files** passed. Compile-time cases reject server handlers in the local API, local handlers in the server API, corporate resources and invalid inputs.
- Actual worker-thread tests perform CPU computation, terminate an infinite loop through cancellation and timeout, simulate worker death, restart successfully, and recover exact receipts. Business rejection and a caught capability failure leave the initial snapshot untouched. Foreign module scope, server-only operations, missing handlers and stale versions are rejected.
- Headless Chromium uses real browser workers and IndexedDB with networking offline. It verifies encrypted profile lock/unlock, exact create retry, revision conflicts between two unlocked sessions, rejected resurrection after profile deletion, and no persistence of an externally mutated snapshot. A worker-side assertion rejects Node, DOM or desktop preload globals. A first diagnostic attempt to inspect short-lived workers after creation raced their termination; the in-worker assertion removes that observation race.
- The existing local-profile interface journey saves a contact, locks and unlocks, and displays the retained record through the new worker path.
- Hidden/minimized Electron saves through the bundled worker, restarts with the same isolated user-data directory, unlocks and edits its encrypted record, then locks again. It checks the vault revision, worker URL, retained data and minimized/unfocused windows. [Native capture](desktop.png).

This does not verify hosted release signing, full-file encrypted native storage, all local-module migration cases, independent local artifact installation, corporate import, full parity or accepted UI polish.
