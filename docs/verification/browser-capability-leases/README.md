# Corporate offline capability leases in browser views

18 September 2026. SDK-05 remains active. This milestone verifies real browser acquisition, cached-view file exports and connected invalidation. Electron offline execution is not implemented; its existing online export boundary remains verified.

## Implemented

- [View lifecycle](../../../packages/shell/src/features/modules/views/device-leases.ts) prepares explicitly opted-in grants through the authenticated API after the signed custom view is verified. It retains request identifiers for uncertain retries, renews before expiry and validates cached grants after offline reload without inventing device-action input. It reports the permitted action kinds and dated expiry using existing UI styling.
- [Corporate view host](../../../packages/shell/src/features/modules/views/custom-view.tsx) preserves live server authorization while connected. Offline exports require device opt-in, the signed declaration and lease, current workspace/view permissions, the matching release, a valid offline workspace window and a fresh guard immediately before the browser effect. Online-only actions still require reconnection. Known server denial never falls back to a cached grant.
- [Workspace policy delivery](../../../packages/shell/src/app/workspace.tsx) records the latest connected revision and invalidates grants on membership/authentication denial. Rejected or stale policy cannot silently restore offline device authority. Pending business work retains its existing recovery behavior.
- [Client guard](../../../packages/client/src/identity/capability-leases.ts) now observes separately authenticated API keys before requesting leases. Within that workspace, rotation invalidates prior grants even if subsequent issuance fails. Generation checks reject delayed key responses; an in-memory denial remains effective if its durable write fails, and an older renewal cannot clear a newer denial while finishing its write. Once storage accepts a later denial check, it removes stale grants so a restarted client cannot recover them.
- [SDK authority validation](../../../packages/sdk/src/contracts/capability-leases.ts) checks the independently supplied issuer, Ed25519 public key and fingerprint. Provenance still comes from the host's authenticated transport, never from a module-supplied token.

The new [browser journey](../../../tests/e2e/corporate-offline-capabilities.spec.ts) builds, signs, reviews and publishes an independent fixture into the isolated registry. Playwright’s managed API receives a disposable Ed25519 signer from the repository test configuration; no production secret or persistent configuration is used. The standard isolated runner passed both affected browser journeys without the earlier local signer helper (`/tmp/gabs-browser-leases-managed-e2e.log`). A reused API must explicitly support test lease signing; the journey reports that prerequisite directly. The normal application acquires and persists the real lease, reloads offline and produces a downloaded file with the expected bytes. It then rejects a real connected permission revocation, an injected known 403 without fallback, corrupted stored signatures and expired workspace access. Expiry retains stored data while removing the action surface. Positive OS notification presentation is not claimed; that fixture's notification declaration intentionally remains online-only.

A later recovery rerun exposed a fixture race: direct corruption could overlap a legitimate locked cache check and be overwritten by its previously verified token. The fixture now waits for offline state and takes the same account lock before installing corruption; its rejection assertion was unchanged. Both the actual browser journey and storage journey then passed twice (**four executions, two distinct journeys**). Log: `/tmp/gabs-browser-leases-recovery-e2e-final.log`. The final 32-test run includes persistence of a known denial once storage recovers.

All completed isolated runners removed their databases. Historical captures written by regression tests were restored. The only new captures are linked above. Initial and final repeated browser runs are not additive acceptance counts.

## Remaining SDK-05 work

**Issuer-wide trust propagation is still missing.** Key observations are currently stored per workspace. Learning a rotation in workspace A does not yet invalidate workspace B’s previously cached key after switching or restarting offline. Implement shared issuer trust, ordered observations and cross-workspace/account restart acceptance before treating the corporate lease guard as complete. This is required implementation, not a deferred feature or a passing test claim.

Then implement main-process-owned, encrypted Electron authority storage and offline effects. The privileged process must independently obtain/verify its API authority and current module/policy context, including after a native dialog. Never trust renderer-supplied roles, keys, leases or connectivity assertions. Exercise hidden native restart, expiry, key rotation, revocation, profile lock and workspace isolation.

Extend corporate SDK/CLI/preview simulation with explicit leased-offline states; its current corporate host simulator still rejects all disconnected device calls. Existing online and standalone simulation evidence does not verify this new policy.

Then continue the [SDK-05 acceptance map](../../sdk-05-acceptance.md): migrate official adapters to public contracts, complete administrator capability review and positive LAN acceptance. Actual notification presentation and web push retain their GOV/OPS gates. No lease permits stock, spending, approval or other corporate business commitments offline. Full parity and the queued UI-refinement goal remain incomplete.
