# Corporate offline device capability leases

SDK-05 implementation in progress. Signed lease contracts, server issuance, the reusable client guard and browser acquisition/policy delivery are implemented and locally verified. [Real cached-view exports](verification/browser-capability-leases/README.md) now pass browser offline acceptance. [Native offline authority](verification/native-capability-leases/README.md) now has local acceptance for independently acquired policy/packages/leases, protected process restart and guarded file effects.

## Authority contract

Modules may declare `offline: "lease"` on `files.export` and `notifications.show`. Omission preserves online-only behavior. The authoring helper rejects lease declarations on LAN capabilities at compile time, and manifest validation rejects them at runtime. LAN transport acceptance remains separate under OPS-01. No capability lease authorizes stock, spending, approval or other corporate business commitments.

The authenticated `moduleCapabilityLease` endpoint requires an identified accepted module version and idempotency key. It checks current identity, membership, module availability, declaration, permission and the workspace offline allowance in a repeatable-read transaction. The allowance is capped at 24 hours; zero disables issuance.

Each signed payload binds the API origin, actor, membership, workspace, module ID/version and full contract digest, alias, capability kind, permission, workspace policy revision, issuance time and expiry. A distinct `suite:corporate-device:v1` purpose prevents confusion with other signed data. A lease cannot transfer to another workspace, release or capability.

The verifier requires a separately trusted API public key and host-owned expected context. It checks signature, exact scope, contract digest, declared eligibility, time window and the latest policy revision known to that host. Clients must recheck these conditions immediately before effects, including after dialogs. The browser does so before offering a download. Electron main independently verifies authority and rechecks it after save dialogs before writing. Its private authority records are outside the renderer cache allowlist, and its configured API issuer must match the signing authority.

## Retries, policy changes and keys

Issuance and its audit entry commit with the idempotency receipt. An unchanged retry returns the same lease and creates no second audit entry. Current authority is checked before reading a previous receipt. Revoked permissions or disabled offline access cannot be bypassed by replaying an old request. A changed policy revision, expired window or signing-key rotation requires a new request identifier.

`CAPABILITY_LEASE_PRIVATE_KEY` supplies an Ed25519 private key through server secret configuration. It is separate from module publication keys. No private key is generated by the API or returned to clients. Missing configuration fails closed with `CAPABILITY_LEASE_UNAVAILABLE`; existing online authorization remains available. The authenticated `capabilityLeaseKey` endpoint returns the public key, its SHA-256 SPKI fingerprint and the independently configured normalized API issuer. The issuer must be learned through the trusted API transport, not copied from the lease being checked. Observing a replacement key invalidates prior grants across the client's cached workspaces and accounts. Public issuer trust and retired fingerprints persist separately from account grants, under a shared browser Web Lock. Account removal preserves that public trust history. Delayed observations/renewals cannot replace a newer shared generation, and retired keys cannot be reused. Legacy workspace-only grants require a fresh connected renewal; they cannot establish shared trust.

An offline host cannot discover new server revocations until it reconnects. Once connected, it must consume the current policy revision and invalidate older leases; otherwise their signed expiry bounds access. The [client store milestone](verification/client-capability-leases/README.md) verifies reusable policy/profile guards, browser persistence and clock rollback handling. It uses persisted time high-water marks and monotonic elapsed time, with a one-second wall-clock adjustment tolerance and connected renewal after detected rollback. The browser view host now acquires eligible grants online, retains retry identifiers, renews before expiry and inspects cached grants after offline reload. Live online authorization remains mandatory while connected; a known denial invalidates grants instead of falling back. Key observations invalidate earlier issuer authority across workspaces/accounts even when subsequent issuance fails. The [shared-trust acceptance](verification/issuer-capability-trust/README.md) covers restart, retirement, persistence failure, acquisition races and legacy cache renewal. Operators must keep the issuer key consistent across API instances and use fresh keys for recovery; hosted rotation/recovery remains OPS-05 acceptance. Browser and hidden native export acceptance are complete within this scope. Corporate leased-offline simulation, official module adoption, administrator review and broader profile/release acceptance remain required.

See the [verification record](verification/capability-leases/README.md) for executed checks and incomplete acceptance.

## Native execution

The native host prepares leases from its own authenticated transport and verified module package. Its private utility-store records retain policy, local opt-in, the verified package and scoped leases; this uses existing encrypted record payloads and does not complete full-file encryption under ID-03. Bootstrap/policy responses update main-owned authorization, while known denials revoke it. A business validation error does not revoke unrelated device grants. Only classified network transport failure permits cached authority; HTTP errors, invalid certificates and programming errors do not. The renderer receives readiness aliases/expiry and opaque host sessions, not signing authority or privileged storage access. Save dialogs are followed by a fresh server check or recheck of the same prepared offline grant.
