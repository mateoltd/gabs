# Corporate offline device capability leases

SDK-05 implementation in progress. Signed lease contracts, server issuance and the reusable client guard/IndexedDB store are implemented and locally verified. Actual browser and desktop acquisition, connected policy delivery and offline effects are not integrated yet; corporate custom-view device actions still require live authorization.

## Authority contract

Modules may declare `offline: "lease"` on `files.export` and `notifications.show`. Omission preserves online-only behavior. The authoring helper rejects lease declarations on LAN capabilities at compile time, and manifest validation rejects them at runtime. LAN transport acceptance remains separate under OPS-01. No capability lease authorizes stock, spending, approval or other corporate business commitments.

The authenticated `moduleCapabilityLease` endpoint requires an identified accepted module version and idempotency key. It checks current identity, membership, module availability, declaration, permission and the workspace offline allowance in a repeatable-read transaction. The allowance is capped at 24 hours; zero disables issuance.

Each signed payload binds the API origin, actor, membership, workspace, module ID/version and full contract digest, alias, capability kind, permission, workspace policy revision, issuance time and expiry. A distinct `suite:corporate-device:v1` purpose prevents confusion with other signed data. A lease cannot transfer to another workspace, release or capability.

The verifier requires a separately trusted API public key and host-owned expected context. It checks signature, exact scope, contract digest, declared eligibility, time window and the latest policy revision known to that host. Clients must recheck these conditions immediately before effects, including after dialogs. That client integration remains unfinished.

## Retries, policy changes and keys

Issuance and its audit entry commit with the idempotency receipt. An unchanged retry returns the same lease and creates no second audit entry. Current authority is checked before reading a previous receipt. Revoked permissions or disabled offline access cannot be bypassed by replaying an old request. A changed policy revision, expired window or signing-key rotation requires a new request identifier.

`CAPABILITY_LEASE_PRIVATE_KEY` supplies an Ed25519 private key through server secret configuration. It is separate from module publication keys. No private key is generated by the API or returned to clients. Missing configuration fails closed with `CAPABILITY_LEASE_UNAVAILABLE`; existing online authorization remains available. The authenticated `capabilityLeaseKey` endpoint returns the public key, its SHA-256 SPKI fingerprint and the independently configured normalized API issuer. The issuer must be learned through the trusted API transport, not copied from the lease being checked. Key rotation invalidates leases signed by the previous key unless future explicit trust-rotation support is added.

An offline host cannot discover new server revocations until it reconnects. Once connected, it must consume the current policy revision and invalidate older leases; otherwise their signed expiry bounds access. The [client store milestone](verification/client-capability-leases/README.md) verifies reusable policy/profile guards, browser persistence and clock rollback handling. It uses persisted time high-water marks and monotonic elapsed time, with a one-second wall-clock adjustment tolerance and connected renewal after detected rollback. Full product integration, main-process-owned native authority and real web/native offline effect acceptance are still required before this feature can be described as usable offline support.

See the [verification record](verification/capability-leases/README.md) for executed checks and incomplete acceptance.
